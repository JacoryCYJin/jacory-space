# Minecraft Skin Studio：AI 制作皮肤 PRD

状态：调研完成，待模型 POC 验证
版本：v0.1
目标仓库：`site/jacory-space-frontend`（客户端）与 `minecraft-studio-service/`（生成服务）
文档类型：产品需求文档
关联文档：[Minecraft Skin Studio PRD](./minecraft-skin-editor-prd.md)

## 1. 产品结论

当前的 AI 皮肤能力不具备上线价值，应停止沿用“通用聊天模型生成固定右臂 JSON 像素”的路线。

本需求将其替换为“AI 生成完整皮肤”的能力：用户用文字或参考图描述角色，系统返回一张完整、可导入 Minecraft 的 64×64 皮肤 PNG；用户在现有 2D UV 和 3D 预览中检查候选，再选择一个进入编辑器细修。

首期不承诺 AI 局部重绘。局部改造应建立在完整皮肤生成质量已通过验证之后，不能以当前固定右臂方案过渡。

## 2. 背景与问题

### 2.1 当前实现

当前实现位于 `src/composables/useAiPartGeneration.js`，工作方式如下：

1. 用户输入描述，可选择让模型查看当前 3D 预览、UV 图和参考图。
2. 浏览器直接调用一个 OpenAI 兼容聊天接口。
3. 通用模型必须返回 Classic 模型右臂、base/outer 两层共 448 个像素的严格 JSON。
4. 前端校验 JSON；不合格时再请求一次“修复 JSON”。
5. 前端把合法像素写入右臂 UV 区域，供用户预览或应用。

这条路径的核心问题不是 JSON 校验不充分，而是模型同时承担了四件不相容的任务：理解人物/服装意图、设计完整服装、理解 Minecraft UV 展开、以逐像素 JSON 精确表达结果。即使 JSON 合法，也常产生不连续、无意义或与身体其他部位不协调的视觉结果。

### 2.2 用户问题

用户描述“酒红色宽松外套右袖，深色袖口”等服装需求时，预期是完整衣身、双袖、领口与外层关系协调的角色设计；当前能力最多尝试重绘一个孤立的右臂，无法满足这一预期。

### 2.3 外部调研结论

公开产品普遍采用“完整皮肤生成 → 2D/3D 检查 → 编辑”的产品流程：

- Photo2Skin 将文字生成定位为可直接游玩的 64×64 皮肤，并引导用户导入编辑器细修。[Text to Skin](https://app.photo2skin.com/text)
- MCSkin 生成完整 64×64 草稿，明确要求用户在 2D 和 3D 中检查噪点、错位和拼接问题。[MCSkin](https://mcskin.app/)
- `/skin` 公开说明使用 Minecraft 专用 SDXL 模型生成底稿，再在浏览器编辑器中完成作品。[About /skin](https://slash.skin/about)

模型研究也支持拆分任务：BLOCK 的研究指出，直接让多模态大模型输出严格 64×64 UV 通常不稳定；其将角色理解和“正反面预览到 UV”翻译拆为两个阶段。[BLOCK 论文](https://arxiv.org/abs/2603.03964)

## 3. 产品目标

### 3.1 首期目标

- 用户可用文字生成一整张可导入 Minecraft 的 64×64 PNG 皮肤。
- 用户可选 Classic 或 Slim，生成结果必须按所选模型预览和校验。
- 用户可添加一张角色或服装参考图；首期不承诺像素级复刻参考图。
- 每次生成提供多个完整候选，用户必须在 2D UV 和 3D 中确认后才可应用。
- 应用一个候选后，皮肤成为现有编辑器中的正常画布，可手绘、撤销、导出。
- 生成质量不满足验收门槛时，不替换当前开发能力，不对外开放入口。

### 3.2 非目标

- 不继续优化或扩展“右臂 JSON 像素生成”。
- 不让 AI 直接覆盖用户当前皮肤。
- 不承诺一次生成就是最终成品；AI 的定位是高质量完整底稿，用户仍可细修。
- 不在首期提供“只改某一只手臂”“保留脸部重绘外套”等局部重绘；该能力留待第二期。
- 不在浏览器中保存或让用户填写第三方模型 API Key。
- 不把模型权重打包进前端静态资源。

## 4. 目标用户与场景

| 用户 | 场景 | 成功结果 |
| --- | --- | --- |
| 普通玩家 | 想迅速得到一个“酒红外套、深色袖口”的新角色 | 选择候选后可下载并在 Minecraft 使用 |
| 有参考图的玩家 | 想把角色立绘/服装灵感转成 Minecraft 风格皮肤 | 生成保留主色、服装层次和显著特征的完整底稿 |
| 皮肤创作者 | 不想从空白 UV 开始，但愿意细修 | 用候选作为起点，在现有编辑器修正细节 |

## 5. 核心体验

### 5.1 入口与创建模式

在“新建皮肤”流程中新增 `AI 制作皮肤`。它与现有的空白皮肤、导入 PNG 并列，不嵌入画笔工具栏。

用户先选择：

- 模型：Classic / Slim；默认 Classic。
- 描述：角色身份、发型、服装、颜色、关键配件。
- 参考图：可选，一张 PNG/JPEG/WebP。
- 候选数量：首期固定 3 张，不向用户暴露推理参数。

### 5.2 文案与提示模板

描述框必须提供可点击示例，而不是要求用户理解 UV、base 或 outer：

- `酒红色宽松外套，黑色内搭和深色袖口，棕色短发，简洁像素风。`
- `蓝银色太空服，深色头盔外层，背部有小型推进器图案。`
- `绿色连帽衫、浅色运动鞋、短黑发，正反面服装细节一致。`

提示词会在服务端转换为模型提示，不要求用户输入“64×64”“UV atlas”等技术术语。

### 5.3 生成与候选检查

```text
填写描述 / 可选参考图
  → 生成中（显示进度与取消）
  → 返回 3 个完整皮肤候选
  → 选择一个候选
  → 同步查看 2D UV、3D 正面、3D 背面
  → 作为新皮肤应用 / 重新生成 / 返回
```

候选卡必须显示：

- 2D UV 缩略图；
- 可旋转 3D 预览；
- 模型类型（Classic / Slim）；
- 校验状态：`可用`、`有外层兼容性提示`、`不可用`；
- 生成批次与候选编号，便于问题复现。

“作为新皮肤应用”前必须明确提示：当前本地草稿会被替换，用户可先导出；应用后生成一次可撤销历史记录。

## 6. 产品流程

### 6.1 从零生成完整皮肤（首期）

1. 用户进入 `AI 制作皮肤`。
2. 用户选择 Classic 或 Slim，填写描述，可上传参考图。
3. 前端上传请求至本产品的生成服务，不直接请求第三方聊天模型。
4. 服务生成 3 张完整皮肤候选 PNG，并执行格式和质量门槛校验。
5. 前端展示通过校验的候选；失败候选不展示为可应用结果。
6. 用户检查所选候选的 UV、正面和背面 3D 预览。
7. 用户应用候选；系统将当前画布存入撤销历史，再替换为候选画布。
8. 用户在现有编辑器中继续修改、导出或丢弃。

### 6.2 重新生成

- 用户可使用同一描述重新生成一批候选。
- 如果生成服务支持 seed，系统记录 seed 供诊断，不在首期 UI 中展示调参控件。
- 已选择但未应用的候选只保留在当前浏览器会话，页面关闭后清理。

### 6.3 未来：基于当前皮肤改造（第二期）

第二期仅在首期质量通过后评估：

1. 用户选择允许修改的身体部位。
2. 系统生成当前皮肤的标准正面/背面参考图。
3. 专用模型生成一张完整协调的新皮肤方案。
4. 程序只合成允许区域的 UV 像素，其他区域逐像素保持原值。
5. 前端高亮差异，用户预览并应用。

不允许再回到“让通用聊天模型单独生成一个肢体的 JSON”方案。

## 7. 模型策略

### 7.1 原则

- 生成服务的产物必须是完整皮肤图像，而非像素操作 JSON。
- 模型选择以实际样例质量为准，不以参数量、论文或宣传替代验收。
- 前端只依赖统一的“完整 PNG 候选”响应，不与任一模型耦合。
- 不将模型选择、API Key 或推理参数暴露给普通用户。

### 7.2 候选 A：Monadical Minecraft Skin Generator XL

这是基于 SDXL 的专用文字到皮肤模型。公开模型卡标注为 3B 参数、OpenRAIL 许可、支持透明外层，并建议以 768×768 推理输出运行。实际 POC 进一步确认该输出含展示图，需提取顶部的旧版 64×32 Classic UV，再用确定性 Minecraft 格式转换生成现代 64×64 纹理；不能直接缩小整张 768 图。[模型卡](https://huggingface.co/monadical-labs/minecraft-skin-generator-sdxl)

适用：作为首个 POC 基线，验证“文本直接生成完整皮肤”的质量与速度。

限制：模型公开页说明它没有通用推理商直接托管；需自托管或使用能部署该模型的 GPU 服务。其许可证不是 Apache/MIT，商用与输出使用必须在接入前完成 OpenRAIL 条款审核。

### 7.3 候选 B：BLOCK v0.6

这是一个面向 Minecraft 的图生图 UV 翻译模型：输入固定构图的角色正反面预览，可附带文字细节，输出皮肤 UV atlas。公开模型卡标注其适配器为 Apache-2.0、4B BF16，基于 FLUX.2-klein-base-4B；该基础模型的公开许可证同为 Apache-2.0，并声明可商业使用。接入前仍须在固定版本上复核模型权重、依赖和托管服务条款。[BLOCK 模型卡](https://huggingface.co/koikin/BLOCKv0.6) [FLUX.2-klein-base-4B 模型卡](https://huggingface.co/black-forest-labs/FLUX.2-klein-base-4B)

适用：复杂服装、参考图和高一致性角色设计；先由图像模型产出规范化正反面角色设计稿，再由 BLOCK 翻译为 UV。

限制：它不是文字到皮肤模型；第一阶段需要独立的图像生成模型。公开模型页同样说明没有通用推理商直接托管，且该模型新、公开样本和使用量有限。

### 7.4 POC 决策

| POC 项目 | Monadical | BLOCK |
| --- | --- | --- |
| 输入 | 文字（首期可不含参考图） | 正反面设计稿 + 文字细节 |
| 输出 | 完整皮肤图像 | 完整 UV atlas 图像 |
| 技术复杂度 | 低 | 高，需要两阶段服务 |
| 作为首期候选 | 是 | 仅在质量明显更优时采用 |

POC 必须用同一组真实需求分别测试两条路线，不能只看模型页示例。通过质量门槛且总体实现成本更低的路线成为首期模型方案；否则不启动接入开发。

## 8. 生成服务与数据契约

### 8.1 架构边界

`site/jacory-space-frontend` 是静态前端，不能承载多 GB 级模型推理。生成能力必须由独立的 `minecraft-studio-service/` 提供：本地开发可运行在本机 GPU/M 系列芯片，线上需要独立 GPU 推理服务。

服务仓库面向 Minecraft 创作能力扩展：皮肤生成是首个模块，后续可增加建筑预览、披风设计等独立模块。它不得复用 `site/` 或 `media-parser/` 的运行时、Python 环境或发布链路；网站仅通过 HTTP API 调用服务。

### 8.2 请求

```json
{
  "model": "classic",
  "prompt": "酒红色宽松外套，黑色内搭和深色袖口，棕色短发",
  "referenceImage": "optional upload reference",
  "candidateCount": 3
}
```

### 8.3 响应

```json
{
  "requestId": "opaque-id",
  "candidates": [
    {
      "id": "candidate-id",
      "skinPng": "temporary PNG URL or binary response",
      "model": "classic",
      "width": 64,
      "height": 64,
      "validation": { "status": "passed", "warnings": [] }
    }
  ]
}
```

禁止返回供前端逐格解析的 AI 像素 JSON。PNG 是候选的唯一内容载体；元数据只用于模型、校验、诊断与生命周期管理。

### 8.4 后处理与校验

服务必须：

1. 将模型原始输出通过模型对应的确定性提取、nearest-neighbor 像素转换与 Minecraft UV 格式转换生成 64×64；禁止直接缩小展示图。
2. 校验 PNG 格式、尺寸、RGBA 通道与透明度。
3. 按 Classic/Slim 生成或校验对应预览，不允许模型类型与预览模型不一致。
4. 识别明显不合格结果：尺寸错误、无法读取、完全透明、单一颜色、非像素化缩放、缺少基础层主体。
5. 为每个候选生成固定视角的正面和背面预览，供用户核查。

自动校验只负责阻止技术无效结果；“服装是否好看、主题是否符合”仍由候选对比与用户确认决定。

## 9. 质量验收

### 9.1 POC 测试集

至少使用以下需求类别，每类不少于 3 条：

- 现代服装：连帽衫、宽松外套、运动装；
- 幻想服装：法师袍、盔甲、披风；
- 明确配色和发型；
- 有参考图的角色概念；
- Classic 与 Slim。

必须包含用户反馈的“酒红色宽松外套，深色袖口”测试样例。

### 9.2 通过门槛

一条路线必须同时满足：

- 100% 输出可读的 64×64 RGBA PNG；
- 100% 能进入现有 3D 预览而不报错；
- 至少 80% 候选在正反面检查时，主体、衣身和双臂不存在明显断裂或错位；
- 至少 80% 候选能识别用户指定的主色和核心服装类别；
- 人工评审认为至少每次生成 3 张中有 1 张可作为“仅需少量手工细修”的底稿。

若没有路线达到门槛，结论应为“不接入”，而不是降低标准上线。

## 10. 隐私、成本与许可

- 用户不提供、前端不保存第三方模型 API Key。
- 用户的描述和参考图只在生成请求期间传给本产品生成服务；候选默认不公开、不进入社区图库。
- 服务端必须限制参考图大小、类型和保留时长；未应用候选在会话结束或过期后删除。
- “开源模型”仅表示可下载权重或源码，不表示推理零成本：本机运行要承担硬件、电力与维护成本，云端运行要承担 GPU 按时或按次费用。
- 使用前必须分别核验：模型权重许可证、基础模型许可证、推理框架许可证、托管服务条款和输出使用限制。

## 11. 埋点与故障诊断

不记录用户 API Key。最小化记录：

- 请求 ID、模型适配器版本、Classic/Slim、是否带参考图；
- 总耗时、候选数、技术校验结果；
- 用户是否应用、重新生成或丢弃；
- 经过脱敏的错误类别。

用于比较候选模型的指标：技术通过率、用户应用率、每次应用前的重生成次数、生成到导出的完成率。

## 12. 里程碑

| 阶段 | 产物 | 退出条件 |
| --- | --- | --- |
| P0：质量 POC | 同提示词下的 Monadical、BLOCK 与当前路线对比图和评分 | 选出通过门槛的路线，或明确不接入 |
| P1：生成服务 | 单一模型适配器、PNG 后处理、校验、临时产物管理 | API 契约与质量测试通过 |
| P2：前端体验 | AI 制作皮肤入口、表单、候选、2D/3D 检查、应用历史 | 用户能完成新皮肤生成到导出 |
| P3：局部改造评估 | 当前皮肤正反面输入、部位白名单合成实验 | 仅在整套生成质量稳定后立项 |

## 13. 开放决策

1. POC 采用本机 M 系列/GPU，还是临时云 GPU；由实际硬件与时延测试决定。
2. Monadical 若通过质量门槛，是否优先选择其较低复杂度路线；BLOCK 仅在质量优势明确时引入。
3. 首期是否允许上传人物参考图，取决于选定模型对参考图的实际保真度。
4. 线上服务采用按次计费、免费额度还是仅本地运行，待 POC 得到单次成本后决定。
